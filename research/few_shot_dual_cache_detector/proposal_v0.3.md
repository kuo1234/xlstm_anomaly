# 研究計畫 v0.3：少樣本通用偵測器的雙快取持續適應（context 優先、回饋選配、兩階段資料）

> 狀態：**研究構想紀錄（research backlog）**。本文件不授權任何訓練、GPU 實驗或標籤存取。啟動前必須另行建立並封存 protocol。
> 日期：2026-09-29。前一版為 [history/proposal_v0.2_dual_cache_detector.md](history/proposal_v0.2_dual_cache_detector.md)。

## 0. 與 v0.2 的差異

| 項目 | v0.2 | v0.3 |
|---|---|---|
| 升格證據 | 以操作員回饋為必要條件 | **context 或內部 context 優先**；操作員回饋改為選配，用來加速與校正 |
| 升格規則 | quarantine＋dwell 後升格 | 持續但**無法解釋**的偏離**不自動升格**（依 toy 模擬結果，見 §3） |
| 資料 | 以 CARE to Compare 為主 | **兩階段**：SMD（與文獻對照、測少樣本跨機台）→ CARE to Compare（真實 context、老化、多種故障型態） |

## 1. 問題

一個凍結的通用偵測器，只給新機台 K 筆正常資料就上線。部署後會碰到兩類狀況：
- **機台老化**：良性漂移，應該被吸收成新的正常。
- **新故障型態**：過去沒見過的異常，應該被記住。

使用者原本的構想：殘差大的區段先放進可疑 cache，經過時間累積或演算法確認後，判定為異常或正常。

## 2. 核心限制：只靠時間無法判定

- repo #3（`research/new_normal_identifiability/`，commit 0f33bcd）已經證明：若良性變化和故障在觀測上的機率分布相同，任何只看訊號的方法最小錯誤率都是 1/2（假設兩者先驗相等）。記憶長短、quarantine、升格規則都無法突破這個資訊上限。
- 「持續就是正常、短暫就是異常」這個 dwell 規則，碰到**持續的故障**（感測器偏移、卡值、緩慢劣化、未修復的故障）和**短暫的良性事件**（測試運轉、啟停機、維修操作）都會判錯。
- 需要的是**訊號歷史以外的證據**，至少一種：
  1. context：負載、設定點、風速、環境溫度等。
  2. 物理或控制約束：例如 power curve、質量與能量平衡。
  3. 內部 context：訓練期學到的通道之間的關係。
  4. 同型機台（peer）：多台同時出現的變化比較可能是共同原因。
  5. 操作員回饋。

## 3. Toy 模擬證據（`toy_identifiability_sim/`）

- 情境 C（良性設定點改變）和 D（感測器偏移故障）的觀測訊號 y 逐點相同，最大差異 8.9e-16。
- 故障步數中有警報的比例，負載週期變化設定：

| 策略 | A 尖峰 | D 偏移 | E 緩慢劣化 | F 長故障後修復 |
|---|---|---|---|---|
| S1 只看訊號＋持續就升格 | 0.95 | 0.01 | 0.00 | 0.02 |
| S2 context＋持續就升格 | 0.85 | 0.10 | 0.25 | 0.38 |
| S3 context＋不自動升格無法解釋的偏離 | 0.85 | 0.98 | 0.50 | 0.96 |

- 固定負載設定下，S1 的 D、E、F 召回率分別為 0.09、0.18、0.35，而且三者都被升格成正常。
- 解讀：
  - 失敗的主因是「持續就升格」這條規則。
  - 一步預測器也會透過 lag **自己跟上**新的水準（週期負載設定下 S1 連升格都不需要）。
  - 緩慢劣化（E）即使有 context 也只有 0.50，需要固定參考加上累積漂移檢定。
- 限制：這是玩具模型（1 個訊號通道＋1 個 context 通道），用 ridge 預測器代替 xLSTMAD-F。「C 和 D 無法區分」的結論與模型無關，但各策略的數值會隨模型與參數改變。

## 4. 方法設計

### 4.1 架構

```
x_t ──► 凍結通用 encoder f_θ ──► z_t
          │ s_b（骨幹分數）        ├─► 正常 cache N（K-shot 錨點＋動態條目）：d_N
          │                        └─► 故障 cache F（確認過的故障，附型態）：sim_F
          ▼
 s = α·s_b + β·d_N + γ·sim_F ─► 閾值 τ（conformal 滾動校準，只用 active 條目）
```

### 4.2 條目生命週期

`suspect/quarantine → active | fault | unresolved → reserve → evicted`

| 證據 | 判定 |
|---|---|
| 偏離很快消失 | 暫判為異常事件；如果之後被駁回，再改寫進正常 cache |
| 持續，且**可被 context 或內部 context 解釋** | 升格進正常 cache（吸收老化） |
| 持續，且**無法解釋** | **unresolved**：不升格，升級警報；若有 peer 或回饋，再依其判定 |
| 操作員駁回 | 寫入正常 cache（選配通道） |
| 操作員確認 | 寫入故障 cache；撤回同一時段已升格的條目（精確回滾） |

防護措施：
- K-shot 的初始條目設為**不可淘汰的錨點**。
- 限制寫入速率。
- 所有寫入都留下紀錄，可以回滾。
- 定期與凍結參考比對，並對緩慢劣化做累積漂移檢定。

### 4.3 三級適應（核心研究問題）

L0 只動 cache／L1 調 α、β、γ、τ 與 cache key（Tip-Adapter-F 式）／L2 小 adapter。三者在**相同證據預算**下比較。

### 4.4 內部 context（SMD 沒有語意 context 時使用）

- 在 train 期學通道之間的迴歸關係：用通道群 A 預測通道群 B，分群以資料驅動的方式決定。
- 負載造成的變化會讓相關通道一起動，仍然可以被解釋；很多故障會破壞這個關係。
- 已知失效情況：協同型多通道故障；會改變通道關係的良性變化。必須如實報告。

## 5. 研究問題

| RQ1 | 用 K-shot 啟用新機台時的偵測能力，以及固定閾值下的誤報率（K 掃描） | SMD（留一台當新機台），CARE（留一座風場） |

## 6. 兩階段資料計畫

**第一階段：SMD（約 4 到 6 週）**
- 已知事實：28 台、38 個匿名且已正規化的通道、每分鐘一筆；以本機兩台為例，train 和 test 各約 23.7k 列（約 16.5 天）；沒有時間戳；每台有 5 到 6 個幾乎不變的通道。
- 適合用來做：RQ1 少樣本跨機台啟用、RQ4、以注入方式量測 false absorption。
- 不適合用來做：真實老化（時間太短）、語意 context、語意故障型態。
- 注意事項：
  - 不使用 point-adjust。
  - 遵守 repo 的標籤存取規定。M1 仍有 19 台的標籤未開過，但 red-team 已指出舊資料清單曾解析全部 28 台標籤，因此不能宣稱它們是完全乾淨的 held-out。

**第二階段：CARE to Compare（Zenodo 14006163）**
- 36 台風機、3 座風場、89 turbine-years、44 個標註的故障事件。
- 有風速和溫度等 context，可以做 power curve 式的正常行為模型。
- 授權為 CC-BY-SA，檔案 5.5 GB。
- 補充資料：MetroPT-3（空壓機）、Tennessee Eastman（控制新故障型態的出現）、MIMII 或 DCASE（跨機台 first-shot）。

## 7. 評估指標

- 偵測：AP、AUROC、不含 point-adjust 的事件 F1、偵測延遲。
- 部署可靠度：固定閾值下正常段的 FPR，以及 FPR 隨時間的變化。
- 適應安全：false absorption 率、故障被吸收後的漏報時長、良性適應延遲、回滾後的殘留影響。
- 新故障：recall@k 次確認。
- 成本：證據或回饋的使用次數、cache 容量、延遲。
- 統計：以機台為單位做 paired bootstrap；margin 事先寫好並封存。

## 8. 新意定位（避免過度宣稱）

**不能宣稱**：
- cache 或 memory bank 本身（PatchCore、Tip-Adapter、TDA、DCASE first-shot 都已經做過）。
- 只看訊號的自我確認正常參考（M2N2、MemStream、CANDI、COMET、AnDri 都已經做過）。
- 只從 X 就能判斷良性或故障。

**可以主張**（依文獻審查，在查詢範圍內未見前例）：
1. G4c：cache-only、輕量微調、adapter 三者在相同證據預算下，附 false-absorption 指標的正面比較。
2. G4d：同一機制同時吸收老化與學習新故障，並量測是否誤吸收故障。
3. G4g：把 Tip-Adapter／TDA 式的 cache 轉移到多變量機台時間序列。
4. 以 context 或內部 context 作為升格證據的准入規則，並評估它的失效條件。

## 9. 停損條件

- 通用骨幹加 cache 在 SMD 上明顯不如逐台訓練 → 改用 fleet 預訓練的骨幹。若仍然不行，RQ1 以負面結果報告。
- 內部 context 在注入實驗中分不出偏移和整體水準改變 → 判定 SMD 做不到 RQ2，改由 CARE 承擔。
- SMD 的異常很少重複出現 → RQ3 不使用 SMD。
- L0、L1、L2 在所有條件下都沒有差異 → 結論為「training-free 就夠」，論文轉向分析 cache 在哪些條件下會失效。
